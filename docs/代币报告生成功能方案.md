# 代币报告生成功能方案

更新时间：2026-04-27

## 1. 目标

在现有产品中新增“代币报告生成”能力，支持用户基于 `symbol` 一键生成一份结构化、可追溯、可导出的研究报告。

本方案不是从零设计一个独立系统，而是基于当前项目已经存在的：

- MySQL 代币基础库
- BigQuery 链上数据
- `server/liveData.ts` 聚合层
- `server/chat/orchestrator.ts` 多数据块编排能力
- `Coin Detail / OnChain Board` 已验证的数据展示逻辑

来落一个可快速上线的产品方案。

---

## 2. 结论先说

当前项目已经具备做出 `MVP 版代币研究报告` 的基础，首期可以稳定覆盖以下内容：

- 项目基本信息
- 官方链接与合约地址
- 融资历史与团队信息
- Tokenomics 分配
- 解锁排期与累计解锁
- 交易所上线与活动记录
- 市场深度 / 成交 / OI / Funding 辅助分析
- 链上 Holder 快照
- 链上资金扩散图

当前不适合在首期承诺“完全自动化、全字段可信”的部分：

- 真实流通率精算拆解
- 空投 / IDO / 交易所活动释放的精确汇总
- 投资人 vesting 后“已转移到非项目地址”的精确判断
- 精确的 Uniswap LP 仓位区间还原
- Twitter follower、Github 活跃度、Docs 完整链接集

所以建议产品分两阶段：

- Phase 1：先做“代币研究简报 / 报告 v1”
- Phase 2：补“真实流通率”和“链上 LP / vesting 专题”

## 5. 建议的报告产品形态

## 5.1 产品入口

建议增加两个入口：

- 入口 A：`Coin Detail` 页新增 `生成研究报告` 按钮
- 入口 B：AI Chat / 报告中心支持直接输入 `symbol` 生成

推荐优先做入口 A，因为：

- 当前详情页已经有 `symbol` 上下文
- 用户心智更自然
- 便于先做单币种报告，不引入额外列表页复杂度

## 5.2 输出形态

首期建议只做两种产物：

- `report_json`
  - 系统真源
  - 供前端渲染、复用、缓存
- `report_markdown`
  - 默认展示与导出基础

二期再补：

- docx
- PDF

原因是当前项目里虽然已有 artifact 概念，但还没有一套稳定的报告导出链路，首期应先把“数据正确 + 结构稳定”做好。

## 5.3 页面形态

建议不是只吐一段长文，而是双层结构：

- 页面层：结构化分章节卡片渲染
- 导出层：渲染成完整 Markdown

这样既适合产品内阅读，也便于后续导出。

## 7. 不建议首期直接照搬的部分

## 7.1 真实流通率分析

你给的目标文档里，`真实流通率分析` 是最有价值的一章，也是最难做对的一章。

当前项目缺口主要在：

- 没有现成的 `ido_events` 聚合接口
- 没有现成的 `airdrop_distribution` 聚合接口
- `exchange_activities` 有活动信息，但不等于“已实际发放数量”
- 没有“投资人已解锁但仍留在 vesting / 项目方地址 / 已转出到外部地址”的稳定口径接口

所以首期如果硬上，风险是：

- 数字会看起来很完整，但事实不一定可靠
- 一旦口径不统一，报告可信度会下降

建议：

- 首期把这一章降级为 `供给释放观察`
- 只展示 `解锁计划 + 上线活动 + 链上大额转账观察`
- 不给出“真实流通率百分比”的确定性结论

## 7.2 初始 LP 添加识别

这里我修正一下判断。

如果 `token_dex_action_raw` 里有 `add / remove` 这类 DEX 行为字段，那么首期不是完全不能做，而是不适合定义成“精确还原 Uniswap LP 设置”，更适合定义成“识别项目早期初始 LP 添加行为”。

### 建议口径

- `add` 视为向池子增加流动性
- `remove` 视为从池子移除流动性
- 最早的大额 `add` 行为，优先视作“疑似项目方初始建池”
- 普通用户小额加池不纳入核心结论

### 首期启发式规则

针对单个 token，按时间升序扫描 `token_dex_action_raw`：

1. 找出最早的 `add` 行为窗口
2. 过滤掉明显的小额 add
3. 按 token 投入数量排序
4. 取最早且金额显著大的记录，标记为“疑似初始 LP 添加”

建议同时参考以下信号：

- 时间很早：位于 token 首次 DEX 行为后的前 `24h / 72h`
- 金额很大：`token amount / totalSupply >= 阈值`，或超过绝对数量阈值
- 地址集中：不是大量散户碎片化小额 add
- 后续行为连续：同地址或同池子后续仍有 add / remove 管理动作

### 首期报告输出建议

首期不要输出过强结论，例如：

- “该地址就是项目方 LP 地址”

建议输出为更稳妥的研究表述：

- “最早大额加池事件”
- “疑似初始 LP 添加”
- “早期流动性建立摘要”

建议字段：

- `firstAddTime`
- `suspectedLpAddress`
- `poolOrRouter`
- `tokenAmountAdded`
- `pairedAssetAmount`
- `pairedAssetSymbol`
- `earlyWindowAddCount`
- `earlyWindowRemoveCount`
- `confidence`
- `note`

### 能做与不能做

这个方法首期可以回答：

- 项目是否存在明显的大额初始建池行为
- 最早加池规模大概是多少
- 后续是否出现明显撤池 / 调池动作

这个方法首期还不能稳定回答：

- 精确 LP 区间上下界
- LP NFT 级别仓位信息
- 100% 确认项目方身份

所以更适合作为报告中的“流动性建立观察”章节，而不是审计级结论。

## 8. 技术实现方案

## 8.1 后端分层建议

建议新增一层独立的 `report` 聚合，而不是让前端逐个调现有接口自行拼。

推荐结构：

```txt
server/
  reports/
    schema.ts
    builder.ts
    renderer.ts
    prompts.ts
    validators.ts
```

职责划分：

- `schema.ts`
  - 定义报告 JSON 结构
- `builder.ts`
  - 并行拉取现有 liveData 数据
  - 做字段归一化
- `renderer.ts`
  - 把 JSON 渲染成 Markdown
- `prompts.ts`
  - 存放每章总结 prompt
- `validators.ts`
  - 做数据完整性和业务规则校验

## 8.2 建议新增 tRPC 接口

```ts
report.generate
report.getBySymbol
report.renderMarkdown
```

建议入参：

```ts
{
  symbol: string;
  asOf?: string;
  mode?: "brief" | "full";
  refresh?: boolean;
}
```

建议返回：

```ts
{
  meta: {
    symbol: string;
    generatedAt: string;
    mode: "brief" | "full";
    completeness: number;
  };
  data: ReportJson;
  markdown: string;
}
```

## 8.3 报告 JSON 结构建议

首期不要直接实现你设计稿里的超大全量 schema，建议先做一个和当前能力匹配的 `ReportJsonV1`。

```ts
type ReportJsonV1 = {
  meta: {
    symbol: string;
    tokenId: number | null;
    generatedAt: string;
    version: "v1";
  };
  overview: {};
  links: {};
  funding: {};
  team: {};
  tokenomics: {};
  listings: {};
  liquidity: {};
  onchain: {};
  narrative: {
    highlights: string[];
    risks: string[];
    conclusion: string;
  };
};
```

这样可以先把系统跑通，再逐步升级到你设计稿里的完整 schema。

## 8.4 数据拉取策略

建议在 `builder.ts` 并行调用：

- `getTokenProfileBySymbol`
- `getTokenUnlockViewBySymbol`
- `getTokenListingViewBySymbol`
- `getTokenKlineBySymbol`
- `getTokenDepthViewBySymbol`
- `getTokenDepthTrendBySymbol`
- `getTokenFundingViewBySymbol`
- `getOnchainHoldersBySymbol`
- `getOnchainFundFlowBySymbol`
- `getOnchainLargeTransfersBySymbol`

然后统一组装。

这部分和当前 `chat/orchestrator.ts` 的思路一致，可以直接借鉴。

## 8.5 LLM 的职责边界

建议严格限制：

- LLM 负责写叙事
- SQL / 数据查询 / 数字计算都由程序完成

LLM 适合生成：

- 项目概览摘要
- 解锁节奏说明
- 上线后流动性观察
- Holder / 资金流解读
- 风险与结论

LLM 不应负责：

- 计算解锁占比
- 计算累计值
- 推导真实流通率
- 拼接原始 SQL

## 9. 校验与风控建议

首期至少要加 4 类校验。

## 9.1 结构校验

- 必填字段是否为空
- 数组是否存在
- 数值字段是否可解析

## 9.2 业务校验

- `circulatingSupply <= totalSupply`
- `marketCap <= fdv` 如超过则标记异常
- `monthlyReleaseRatio` 与 `unlockAmount / totalSupply` 是否一致
- `cumulativeRelease` 是否单调递增

## 9.3 数据缺失降级

如果某块数据缺失：

- 章节保留
- 明示“暂无可验证数据”
- 不让 LLM 补编

## 9.4 结论边界控制

如果缺少以下数据，不要生成过强结论：

- 缺少链上数据时，不下“筹码正在集中/分散”的定性判断
- 缺少解锁数据时，不下“未来解锁压力大/小”的确定性判断
- 缺少活动发放实数时，不下“真实流通率已达 xx%”判断

## 12. 我对当前项目的最终建议

如果目标是“尽快把代币报告能力放进产品里”，最合适的路径不是一次性做成你设计稿里的完整终局版，而是：

1. 先基于现有 `liveData + chat orchestration` 做 `报告 v1`
2. 把可验证的数据章节先做扎实
3. 把“真实流通率”和“LP 设置”明确列为二期能力

这样做的好处：

- 上线快
- 可信度高
- 和现有系统复用度高
- 不会为了追求完整结构而引入大量高风险“半真半假”的字段

一句话总结：

当前项目已经足够支撑“研究简报型代币报告”，不够支撑“全自动精算型深度研究报告”。首期应做前者，二期再补后者。
