# 地址标签系统方案说明

> 这份文档给产品、运营、研发同事快速理解用，不展开实现细节。

---

## 1. 这个系统是干什么的

我们需要给某个代币下的重要地址打上“项目方团队、投资人、空投合约、交易所热钱包、DEX 池子”等标签。

这些标签不是全局地址画像，而是**围绕某个 token 的专项判断**，因此系统按 `token + chain` 来做。

系统的目标不是一次性自动判断所有地址，而是：

- 先由规则引擎给出候选标签
- 再由人工审核把关
- 最后把审核通过的结果沉淀成生产标签，供调研报告等下游使用

---

## 2. 为什么要这样做

现有外部标签有几个问题：

- 不是按 token 定义的
- 覆盖不完整
- 对“团队金库、投资人解锁、空投分发”这类项目内部结构识别不够强

而我们自己有一些更有价值的先验信息：

- `token_allocation`
- `token_unlocks`
- 项目研究过程中的上下文

所以更合理的方式不是直接依赖第三方标签，而是做一套**内部、可审核、可追溯**的标签流水线。

---

## 3. 系统怎么工作

流程很简单：

```text
运营选代币 -> 系统跑分析 -> 生成候选标签 -> 人工审核 -> 审核通过后入库 -> 报告使用
```

拆开看就是 5 步：

1. 运营在页面上选择一个代币和链
2. 系统运行 detector，生成一批候选标签 proposal
3. 每条 proposal 都带理由和证据
4. 审核员逐条批准或拒绝
5. 批准的 proposal 写入正式标签表

---

## 4. 系统里有哪三类核心数据

### 4.1 run

表示“一次分析任务”。

它记录：

- 分析的是哪个 token
- 谁触发的
- 什么时候开始和结束
- 成功还是失败
- 这次产生了多少 proposal

### 4.2 proposal

表示“系统提出的一条待审核判断”。

比如：

- `0xabc...` 可能是 `team_vault`
- `0xdef...` 可能是 `airdrop_distributor`

每条 proposal 必须带：

- 候选标签
- 置信度
- 一句话理由
- 结构化证据

### 4.3 label

表示“已经审核通过、正式生效的标签”。

下游系统只读这里，不直接读 proposal。

---

## 5. 为什么一定要人工审核

因为很多地址判断本质上是高价值推断，不适合完全自动入库。

比如：

- 团队金库和投资人金库可能在初始分配上很接近
- 空投分发和活动奖励在行为上可能相似
- 某些地址可能同时像路由合约，也像中转钱包

所以 detector 的职责是“给出有依据的建议”，不是“直接写最终答案”。

人工审核可以保证：

- 生产标签更可信
- 错误可控
- 后续争议有证据可回看

---

## 6. 这版方案为什么刻意做简单

为了尽快做出可靠闭环，这版明确做了几件“减法”：

- run 状态只保留 `running / success / failed`
- proposal 状态只保留 `pending / approved / rejected`
- 不做自动训练
- 不做复杂权限模型
- 不做复杂并发和分阶段编排

这样做的好处是：

- 代码更容易实现
- 审核逻辑更容易理解
- 出问题更容易排查
- 后面加 detector 时不会把系统本身搞复杂

---

## 7. 标签是怎么定义的

系统里所有 label 都统一在一个字典文件里定义。

字典里会写清楚：

- 标签名
- 中文展示名
- 属于哪一类
- 典型识别规则
- 推荐 subtype
- 和哪些标签冲突

这样做的好处是：

- 研发、运营、产品对术语统一
- UI 和后端不用各自维护一套枚举
- 文档可以从字典自动生成

---

## 8. 这版优先做哪些标签

MVP 先做最有价值、最容易验证的一类：

- `team_vault`
- `investor_vault`
- `ecosystem_vault`
- `foundation_vault`
- `community_vault`

也就是先从 `tokenomics_match` 开始。

原因很简单：

- 这类标签跟 `token_allocation` 的先验最强
- 证据最容易解释
- 对调研报告价值最高

后面再逐步补：

- `downstream_inherit`
- `airdrop_pattern`
- `vesting_pattern`
- `cex_pattern`
- `dex_pattern`

---

## 9. 标签怎么更新

如果同一个地址、同一个 token、同一个 label 以后又有新的审核结果：

- 老记录不会删
- 老记录会失效
- 新记录成为 active 版本

所以这个系统支持：

- 追溯历史
- 后续纠正
- 审核结果迭代

这点对研究场景很重要，因为项目认知本来就会随着数据补充而变化。

---

## 10. 对同事最重要的协作约定

### 产品 / 运营

- 不直接改数据库标签
- 所有生产标签都通过审核页进入
- 审核时尽量写清楚拒绝原因

### 后端

- detector 只产出 proposal，不直接写生产表
- 审核通过写入 `address_labels` 必须走事务
- 所有地址统一小写

### 前端

- 审核页优先保证可读性，不要过度追求复杂交互
- 一条 proposal 必须把“标签、理由、证据、操作”放在同一屏里

### 调研报告消费方

- 只读取 `address_labels` 中 `is_active = true` 的记录
- 不直接消费 proposal

---

## 11. 一句话总结

这是一个“**规则先提议、人工再确认、结果可追溯**”的 token 级地址标签系统。

它的重点不是一开始把识别逻辑做得多复杂，而是先把“分析、审核、入库、消费”这条主链路做稳定。
